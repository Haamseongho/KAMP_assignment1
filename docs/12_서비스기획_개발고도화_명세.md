## 서비스 기획 및 개발·고도화 명세 v1.0

- 작성일: 2026-09-26
- 과제: 제조기업의 생산성 향상 및 작업환경 개선을 위한 아이디어 제시 및 AI 알고리즘 구현
- 제안 제품명: **MoldGuard**. 기존 프로젝트명을 유지하고 서비스 기능을 확장한다.
- 문서 성격: 첨부 5개 보고서를 근거로 한 **신규 서비스 설계 및 개발 제안**. 신규 기능이 구현됐거나 현장 효과가 검증됐다는 보고서가 아니다.

- 제외: 대회 제출 대행, 모델 재학습 수행, 실제 저장소 수정, 설비 자동제어, 검사 생략.

## 1. 서비스 방향: 무엇을 조기에 해결하는가

### 1.1 해결하려는 업무 문제

[기존 근거] 과제는 공정 종료 후 검사로 이상을 확인하는 방식의 한계를 다룬다. 현재 모델은 `Cycle_Time` 등 샷 전체 요약값을 사용하므로 검증 가능한 예측 위치는 **공정 종료 후·최종검사 전**이다. 실제 변수 도착 시각은 아직 미확인이다. [S1 §1, S2]

[신규 제안] 서비스의 중심 문제를 다음과 같이 정의한다.

> 검사 결과를 기다리는 동안 어떤 제품을 먼저 확인할지, AI 판단을 어느 조건에서 믿지 말아야 할지, 의심 상황을 누가 확인하고 어떤 기록을 남길지 일관되게 관리하기 어렵다.

해결 대상은 세 종류다. **발견 지연**에는 검사 우선순위를, **예측 오판 위험**에는 적용 범위 제한과 기존 검사 복귀를, **반복 문제 대응 지연**에는 담당자·표준 점검·조치 이력을 연결한다. 마지막 효과는 후속 생산과 조치 시각 데이터로 별도 검증한다.

### 1.2 ‘예방’을 세 단계로 나눈다

| 단계 | 시점과 목표 | 현재 상태 | 가능한 주장 |
|---|---|---|---|
| A. 검사 전 선별 | 샷 종료 후, 최종검사 전에 먼저 확인할 대상을 찾음 | 기존 연구 범위. 현장 가용성·라벨 미확정 | 검사 순위의 연구용 비교·진단 |
| B. 반복불량 확산 방지 지원 | 앞선 샷의 징후·확인 결과로 후속 생산 점검을 요청 | 시각·샷/로트·조치 이력 및 승인 필요 | 후속 불량의 조기 대응을 지원하도록 설계 |
| C. 공정 중 조기경보 | 현재 샷의 진행 중 일부 신호만으로 이후 품질 위험을 예측 | 원시 시계열·단계별 도착 시각 필요 | 별도 early-warning 모델의 미래 연구 목표 |

A는 이미 만들어진 해당 제품의 불량을 되돌리는 기능이 아니다. B 역시 알림과 점검만으로 불량 예방 효과가 입증되지 않는다. C에서 샷 전체 `Cycle_Time`, 최종 최대압력 등 미래에 확정되는 요약값을 사용하면 안 된다. 각 단계는 서로 다른 예측 시점·입력·검증 계약을 가진다. [A의 근거: S1 §1. B·C는 신규 제안]

### 1.3 한 문장 서비스 설명

**MoldGuard는 사출 공정데이터를 이용해 최종검사 전 위험도를 연구·평가하고, 검증된 범위에서 우선 확인 대상과 표준 점검 절차를 연결하며, 미검증 상황에서는 기존 검사를 유지하는 작업자 지원 서비스다.**

발표 제목 예시: **“MoldGuard: 실패조건을 아는 AI 기반 검사 전 위험 선별 및 반복불량 대응 지원”**.

### 1.4 성공의 정의

개발 성공과 현장 효과를 분리한다. 현재 데이터만으로도 재현 가능한 AI 비교·실패 분석·정책 엔진·조회 화면·조치 기록 체계는 개발할 수 있다. 현장 효과의 성공은 새 기간 데이터와 실제 운영에서 불량 확인 시간, 검사 지연, 알림 부담, 조치 이행을 비교한 뒤 판단한다.

**모델이 나아지지 않아도 ‘미검증 설비의 잘못된 자동 사용을 막고, 어디에 추가 정보를 수집해야 하는지 제시하는 서비스’는 개발 성과다. 다만 이를 실제 불량률 감소 성과로 바꿔 쓰지 않는다.**

## 2. 기존 실험을 서비스 요구사항으로 번역

### 2.1 중요한 제약과 대응

| 기존 근거 | 해석 | 신규 서비스 요구사항 |
|---|---|---|
| 라벨 2,393행 중 숫자 1은 42행. `1=불량` 미확정 | 평가 지표의 불량 의미가 조건부 | 라벨 계약 화면, 증거·파일 해시 연결, 미확정 시 ‘숫자 라벨 1’로 표시 |
| 동일 센서값·상반 라벨 36그룹, 숫자 양성 42개 중 36개 포함 | 현재 입력만으로 구별 불가능한 관측이 존재 | 제품↔샷↔캐비티 추적, 상충 원인 확인 업무, 임의 삭제·다수결 정답 금지 |

| 원점수 평균 29.6837%, 관측 양성률 1.7250% | 원점수를 불량 확률로 표시하면 오해 | 모델점수와 확률 분리. 승인 전 `defect_probability=null` |
| 비라벨 71,180행 중 OOD 플래그 27,357행(38.43%) | 학습범위와 다른 데이터가 많음. 결함 비율 아님 | 데이터 범위 경고, OOD에서 정상 판정·위험 0 처리 금지 |
| 파일별 정규화가 의심되고 원시 스케일러 미확인 | 원시 단위 해석·미래 추론 비교 가능성 미확정 | 원시단위·변환기 계약, 신규 배치별 재정규화 금지 |
| 기존 480행 홀드아웃은 이미 분석에 사용됨 | 새 후보의 독립 최종 시험으로 재사용 불가 | 새 기간 동결 평가와 개발 평가 분리 |
| 과거 outputs를 전제로 하는 고정 경로 | 새 clone에서 실행이 막힐 수 있음 | `--data-dir`, `--split-dir`, 독립 분할 생성, 검사 범위 분리 |

근거: S1 §1–4, S3 §2, S4 표 및 해석, S5 P0-A·현재 근거. 위 수치는 서로 다른 실험 범위를 섞어서 하나의 성능으로 제시하지 않는다.

### 2.2 현재 결과를 어떻게 말해야 하는가

S1의 과거 홀드아웃 AP 전체 0.2779, CN7 0.6392, RG3 0.0192는 해당 480행 평가에 대한 기록이다. S4의 전체 0.1154는 개발 OOF 결과다. 두 숫자의 차이를 성능 하락이나 개선으로 해석하지 않는다. CN7의 홀드아웃 Top 10%에서 4/4를 찾은 것은 불량 가정 사례 4건의 결과이며 현장 재현율 100% 보장이 아니다. [S1 §2, S4]

S3의 보정 Brier 0.016695와 발생률 상수 0.016954 차이는 보고된 95% 구간에 0을 포함한다. 확률보정 연구를 이미 했다는 점은 보존하되, 운영 확률이 확보됐다고 주장하지 않는다. fold 내 순위가 보존돼도 fold별 보정 척도를 합친 OOF AP가 달라질 수 있다는 기존 설명도 보존한다. [S3 §2]

### 2.3 지금의 실제 승인 상태

**현재 모든 행은 기존 검사 유지 대상이다.** CN7의 연구 결과가 RG3보다 낫다는 이유로 CN7만 즉시 현장에 적용하지 않는다. 라벨·시점·평가단위 계약과 새 기간 검증이 남아 있다. 기존 `action`은 다음을 보존한다. [S1 §4, S2 중단조건]

| 현재 집단 | 기존 기록의 행 수 | 기존 action |
|---|---:|---|
| RG3 전체 | 35,941 | `usual_inspection_unvalidated_machine` |
| CN7 OOD | 19,607 | `usual_inspection_ood` |
| CN7 나머지 | 15,632 | `usual_inspection_label_unconfirmed` |

합계 71,180행이다. 신규 서비스는 이 상태를 숨기지 않고 **‘연구용 순위 / 실제 검사 변경 없음’** 배너로 표시한다. 집계는 원래 산출물이 존재할 때 읽어서 검증한다. 위 숫자를 데모용 실시간 운영 데이터로 주입하지 않는다.

## 3. 사용자와 업무 흐름

### 3.1 역할

| 역할 | 주요 질문 | 서비스 권한 |
|---|---|---|
| 검사 담당자 | 지금 무엇부터 확인해야 하나? 이 추천을 사용해도 되나? | 승인된 대기열 조회, 확인·인수인계 기록 |
| 공정·품질 담당자 | 반복되는 문제가 무엇이고 어떤 점검이 필요한가? | 사건 확인, 승인된 SOP 연결, 조치 기록, 오류 검토 |
| 모델 관리자 | 어느 조건에서 실패하는가? 배포해도 되는가? | 실험·검증·모델카드 관리, 배포 신청 |
| 현장 승인자 | 검사 규정과 운영 위험을 만족하는가? | 적용 범위·정책 승인/철회, 긴급 복귀 |

개인 작업자를 모델로 점수화하거나 인사평가에 쓰는 기능은 범위에서 제외한다. 운영 기록은 문제 대응 개선에 필요한 최소 범위로 수집한다.

### 3.2 기본 흐름

```text
CSV/현장 이벤트 수신
  → 스키마·라벨·단위·시점·식별자 계약 확인
  → 입력 가용성 확인 및 모델 추론
  → 설비/조건별 검증 범위, OOD, 버전·지연 확인
  → 연구용 결과 또는 승인된 현장 참고 추천
  → 기존 필수검사를 유지하며 작업자 확인
  → 필요 시 승인된 점검표와 담당자 연결
  → 최종검사·조치 결과를 제품/샷에 연결
  → 실패조건 분석과 새 모델 후보 검증
```

현재 단계에서는 연구용 분석 뒤 실제 운영 변경 없이 기존 검사로 복귀한다. 데이터가 없어도 ‘계약 미확인 목록’과 ‘필요한 데이터’는 표시할 수 있다. 시각이 없는 현재 CSV를 시간순 스트리밍으로 재생한 것처럼 연출하지 않는다.

### 3.3 세 종류의 메시지를 구분

1. **품질 위험 참고**: 라벨·시점·성능이 검증된 범위의 모델 점수에 기반한 우선 확인 제안. 현재는 연구 전용.
2. **데이터/모델 상태 경고**: 입력 누락, 미검증 설비, 학습범위 밖, 모델 만료. 이는 불량 발생 경보가 아니다.
3. **점검 업무 요청**: 담당자와 승인된 SOP를 연결한 확인 업무. 설비 제어 명령이 아니다.

이 구분은 RG3의 낮은 성능을 억지로 품질 알림으로 바꾸지 않고, ‘이 조건에서는 AI 판단을 보류해야 한다’는 유용한 정보로 연결하기 위한 신규 설계다.

## 4. 핵심 기능 정의

### F01. 데이터 계약·준비 상태 센터 — P0

파일 해시별로 라벨 코드, 단위, 제품/샷/캐비티 관계, 변수 도착 시각, 검사 확정 시각, 원시 스케일러를 `confirmed / unconfirmed / mismatch`로 관리한다. 확인은 텍스트 체크만이 아니라 근거 파일 해시·검토자·확인일·적용 범위를 가진다.

- 원본 파일 원형과 SHA-256 보관. 이름만 같은 다른 파일은 별도 버전이다.
- 원본 숫자 라벨과 의미 라벨을 분리한다. 코드북 승인 뒤에도 원본을 덮어쓰지 않는다.
- CN7/RG3는 기존 문서의 설비 구분으로 유지하되, 실제 물리 설비·제품군 매핑은 새 계약으로 확인한다.
- 새 데이터/스케일러/스키마/대상 설비가 달라지면 이전 승인 범위를 자동으로 재사용하지 않는다.
- 키·시각이 없으면 기능이 비활성화된 이유와 필요한 필드를 표시한다.

**완료 기준:** 미확인 값을 UI에서 임의로 ‘확인’으로 표시하지 않으며, 계약 없이 현장 적용 모드를 켜려 하면 차단된다. 기준: S2, S5 P0-B.

### F02. 검사 전 모델점수·우선 확인 대기열 — P1 / 현장 활성화는 P2 이후

연구 화면에서는 현재 점수, 설비 내 순위, Top-10%/20% 정책의 차이, OOD 여부와 미승인 사유를 보여준다. `risk_score`라는 기존 필드는 호환성을 위해 유지하되 UI 명칭은 라벨 확정 전 **‘숫자 라벨 1 예측 점수’**로 한다.

운영 우선순위는 점수와 분리한다. `research_priority`는 계산 가능하지만 `operational_priority`는 승인 전 `null`이다. 승인 이후에도 낮은 점수를 ‘안전/검사 불필요’로 해석하지 않는다. 현재 HIGH/REVIEW/STANDARD는 오프라인 참고 분류다. [S1 §4]

실제 대기열이 연결되면 도착한 제품만 선택할 수 있고, 기존 필수·긴급 검사 규칙, 자격 있는 검사 자원, 대기 상한을 우선한다. AI가 적용되지 않는 설비의 기존 서비스 수준을 희생해 적용 설비만 빨리 처리하지 않는다. 세부 정책은 §7에 정의한다.

**완료 기준:** 라벨 미확정, 미검증 설비, OOD, 입력 오류에서 추천과 실제 action이 섞이지 않는다. 최초 구현은 물리 대기열을 변경하는 API를 제공하지 않는다.

### F03. 적용 가능성·실패조건 설명 카드 — P1

한 개의 ‘신뢰도 92%’ 대신 확인된 근거와 미확인 조건을 제시한다.

- 입력 계약 통과 여부, 설비/조건의 승인 여부, OOD 플래그.
- 관련 검증 영역의 행·그룹·양성 수, 평가 기간과 버전.
- 해당 영역의 AP, Top-K 회수 수, 미탐·오경보와 불확실성.
- 점수에 연관된 특징과 학습분포 내 위치. 원시 단위가 없으면 표준화 값으로 명시.
- 설명 문구: ‘예측 연관 요인’과 ‘확인할 항목’. 원인 확정·처방으로 표현하지 않음.

기존 조건분석 예시: CN7 `Clamp_Close_Time` 학습 중앙값 초과 영역에서 개발 양성 13행이 모두 있었지만 TP 9/FN 4였다. RG3 `Max_Switch_Over_Pressure` 중앙값 초과 영역의 음성 중 오경보는 149/400(37.25%)였다. 이 수치는 **연구용 조건 설명**이며 ‘시간을 줄이거나 압력을 낮추면 해결’이라는 공정 규칙이 아니다. [S3 §3]

상충 라벨 그룹 여부는 과거 평가에서 분석할 수 있는 진단 정보다. 아직 검사 결과가 없는 신규 제품의 미래 라벨을 보고 ‘상충 그룹’으로 판정하는 운영 로직을 만들지 않는다.

**완료 기준:** 양성 0건은 ‘안전’이 아니라 ‘검증에 양성 사례 없음’으로 표시한다. 단일 행에 통계적 신뢰구간이 있는 것처럼 집단 구간을 붙이지 않는다.

### F04. 표준 점검·조치 업무 관리 — P1, 실제 점검표는 현장 승인 필요

점수 하나를 보는 데서 끝나지 않고 ‘무엇을 확인하고 누가 후속 처리하는가’를 남긴다.

| 상황 | 제공할 업무 카드 | 하지 않을 일 |
|---|---|---|
| 검증된 영역의 우선 확인 추천 | 제품/샷 확인, 승인된 검사 순서 참고, 담당자 확인 | 검사 생략 또는 자동 불합격 판정 |
| 입력 누락/단위 불일치 | 수집·매핑 확인 요청, 관련 데이터 격리, 기존 검사 유지 | 누락을 정상값이나 위험 0으로 대체 |
| RG3 성능 미확인 | AI 적용 보류 사유, 추가 검증·라벨 연결 요청 | 근거 없는 품질 위험 알림 폭주 |
| 반복 신호/연속 불량 확인 | 관련 샷·로트 확인, 승인된 점검표, 책임자 검토 | 압력·온도 자동 변경, 설비 자동 정지 |
| 검사 결과 연결 모순 | 제품·캐비티 연결 및 검사 판정 검토 요청 | 다수결로 정답 변경 |

점검표 예시는 ‘원재료/금형/센서/설정 이력 확인 항목을 담당자가 검토’ 수준의 **템플릿**으로만 제공한다. 원문에 없는 구체적 고장 원인이나 온도·압력 설정치를 생성하지 않는다. 원문 SOP가 없으면 `template_unapproved` 상태로 표시하고 현장 절차처럼 배포하지 않는다.

사건 상태 제안: `OPEN → ACKNOWLEDGED → INVESTIGATING → ACTION_RECORDED → VERIFIED_CLOSED`. 오경보·중복은 별도 사유로 종료할 수 있다. 단순히 알림을 읽었다고 효과 검증 완료로 처리하지 않는다.

### F05. 반복불량 확산 방지 지원 — P2 이후

[조건부 확장] 실제 시간·샷·제품·금형/레시피·로트·조치 기록이 있으면, 동일 조건의 반복 신호를 하나의 사건으로 묶고 후속 생산 점검을 요청한다.

- 이전 샷의 **당시 가용한** 센서 요약과 확정된 검사 결과만 과거 정보로 사용한다.
- 원시 공정값의 이동 통계 또는 EWMA 같은 변화감지 기준선을 먼저 비교한다.
- 제품/레시피 전환, 정비 후 재시작 등 기준 분포가 달라지는 이벤트를 구분한다.
- 임계값·지속 조건·해제 조건·중복 알림 제한은 과거 개발 기간에서 정하고 새 기간에서 검증한다.
- 반복 신호를 자동 원인 진단이나 불량 확정으로 해석하지 않는다.
- 승인된 점검과 조치 전후를 연결하지만, 전후 수치 차이만으로 예방의 인과효과를 선언하지 않는다.

EWMA는 과거 관측의 가중치를 점차 줄이는 방식으로 작은/점진적 변화에 민감하게 설계할 수 있는 관리도 방법이다. 대표성 있는 기준 기간이 중요하다. [W3] 이 프로젝트에서는 시간·단위·기준선이 확인되기 전 구현해도 비활성 연구 모듈로만 남긴다. 자동상관·조건 전환·다중 변수 알림 부담에 대한 검증 계획도 필요하다.

**완료 기준:** 동일 사건의 중복 알림이 합쳐지고, 발생·확인·조치·후속 확인 시각이 연결된다. 실제 미래 불량 감소는 별도 현장 평가 전까지 ‘미검증’이다.

### F06. 검사 결과 회수·오류 학습 센터 — P1 기반 / P2 실데이터

AI가 우선 확인한 표본뿐 아니라 기존 필수검사 전체 결과를 회수한다. `pending / confirmed / corrected / invalidated` 상태를 구분하고 미도착 라벨을 정상으로 채우지 않는다.

성능 대시보드는 라벨 확정이 끝난 평가 구간만 기본 집계한다. 최신 미완료 구간의 라벨 도착률·대기 건수를 별도로 표시한다. 우선검사 대상만 빨리 결과가 나와 전체보다 성능이 좋아 보이는 현상을 막기 위해 표본 선택 상태를 기록한다.

추가 확인 업무는 RG3, OOD, 상충 라벨 연결 사례에 집중할 수 있으나, 평가용 데이터는 대표성을 유지해 별도로 확보한다. 학습 후보 데이터 선택과 최종 성능평가 표본을 동일시하지 않는다.

**완료 기준:** 정정 라벨의 이전 값과 변경 사유가 남고, 데이터가 새로 들어왔다고 자동 재학습·자동 승격하지 않는다.

### F07. 검사 대기열 비교·효과 평가 — P2

현재는 정적 Top-K 발견율만 분석한다. 실제 검사 가능 시각·검사 시작/종료·자원·긴급 규칙을 받으면 현행 정책/FIFO와 AI 보조 정책을 같은 조건으로 재생한다. [S2, S5 P2]

비교 결과에는 불량 확인까지의 시간뿐 아니라 전체 대기시간, 설비별 지연, 긴급 규칙 위반, 최대 대기 상한 위반을 함께 표시한다. 현행이 FIFO가 아니면 현행 정책을 주 대조군으로 하고 FIFO는 추가 대조군으로 둔다.

오프라인 재생은 반사실 가정이 있는 시뮬레이션이다. 검사 순서 변경 시 검사시간·셋업이 달라질 수 있음을 명시한다. 과거 실제 검사 소요시간을 고정 사용한다면 ‘제품별 소요시간이 정책에 따라 변하지 않는다’는 가정을 보고하고 민감도 분석한다. 이 재생만으로 실제 작업환경·불량률 개선을 증명하지 않는다.

### F08. 모델 운영·재현·감사 기록 — P0부터

기존 스크립트를 서비스에서 호출할 수 있도록 얇은 어댑터를 만들고 기존 실험 결과와 기준선은 유지한다. 새 실험은 새 출력 폴더를 쓴다. 데이터 계약, 분할, 코드, 모델, 정책, UI 집계가 하나의 버전 사슬로 연결되게 한다.

기록: Git 커밋/dirty 여부, 원본/분할/코드/모델 해시, 패키지 전체 버전, 명령, seed, 실행 시작/종료·종료코드, 실행/생략/실패 시험, 채택 사유. 현재 테스트 수 11·18·19는 각 문서의 다른 시점/범위 기록이며 합산하거나 최신 전체 통과 수로 표시하지 않는다. [S1 §6, S3 §4, S4, S5]

## 5. 화면과 데모 범위

### 5.1 초기 화면은 다섯 개로 제한

| 화면 | 핵심 구성 | 현재 데이터로 표시할 수 없는 것 |
|---|---|---|
| 데이터 준비 상태 | 파일별 계약, 누락 증거, 원본 해시, 검증 로그 | 확인되지 않은 라벨 의미·실제 시각 |
| 연구용 검사 순위 | 모델 점수·설비별 순위·OOD·기존 검사 유지 | 승인된 실시간 우선검사·불량 확률 |
| 설비/조건별 실패 분석 | 전체/CN7/RG3, 표본 수, AP·회수 수·미탐·오경보 | 미확보 후속 기간 성능 |
| 점검·조치 업무 | 템플릿, 담당자, 상태, 증거·결과 연결 | 실제 현장 SOP 승인 또는 조치 효과 |
| 모델 검증·승인 | 실험 비교, 데이터/모델 버전, 승인 범위·철회 | 날짜 도달만으로 완료된 현장 승인 |

상단 배너의 기본값은 **“연구 모드 · 라벨/시점 계약 미확인 · 전량 기존 검사 유지”**다. ‘시스템 정상’과 ‘제품 정상’을 같은 녹색 상태로 표현하지 않는다.

### 5.2 시연 흐름

실제 산출물이 있으면 로드해 데이터 제약을 먼저 보여주고, 전체 지표와 RG3 지표의 차이를 설명한다. 동일한 점수라도 계약·설비 검증·OOD에 따라 추천이 보류되는 정책 테스트를 시연한다. 이어 점검 업무 템플릿과 후속 데이터 요청, 새 기간 검증 계획을 보여준다.

원본 CSV·산출물이 없는 경우에는 파일 선택/빈 상태/정책 단위 테스트만 시연한다. 테스트 전용 고정 객체는 `TEST_ONLY` 표시와 별도 경로를 쓰며 실제 제조 기록·시간·불량률로 제시하지 않는다. UI를 채우기 위해 제조데이터를 합성하거나 기존 CSV에 가상 시간을 붙이지 않는다.

## 6. 데이터 모델과 시점 계약

### 6.1 두 종류의 데이터 계약을 분리

**LegacyResearchRecord**는 현재 CSV용이다. 파일 해시, 원본 행 ID, CN7/RG3, 원본 수치 24개, 선택적 숫자 라벨을 보존한다. 모델 입력은 기존 구현에 따라 `Clamp_Open_Position`을 제외한 공정 23개와 설비 표시이며, `PassOrFail`과 `Unnamed: 0`은 입력에서 제외한다. 동일값 그룹 정의는 기존과 같이 같은 설비의 원본 24개 공정값을 사용한다. ID는 추적용이지 특징이 아니다. [S1 §1–2]

**OperationalObservation**은 미래 현장용이다. 샷·제품·캐비티·실제 시각·원시단위·변환기 버전이 확인된 데이터에만 사용한다. 현재 행 ID를 샷 ID나 제품 ID로 자동 복사하지 않는다.

기술상 `observation_uid`는 파일 해시+설비+원본 행 ID 등을 해시해 생성할 수 있다. 이는 현재 레코드의 고유 추적 키일 뿐 물리 제품 식별자가 아니다. 데이터 버전이 달라지면 다른 UID가 된다. 원본 키 보존과 추적 가능성이 우선이다.

### 6.2 신규 테이블/객체 제안

| 객체 | 주요 필드 | 사용 조건 |
|---|---|---|
| `dataset_versions` | dataset_id, source_sha256, schema_version, target_semantics, transform_version | 원본·전처리 이력 |
| `data_contract_checks` | item, status, evidence_uri, evidence_hash, reviewer, confirmed_at, scope | 계약 승인 근거 |
| `observations` | observation_uid, dataset_id, machine, source_row_id, shot_id?, product_id?, cavity_id?, feature_snapshot_id | 현재/현장 단위를 구분 |
| `feature_snapshots` | cutoff_at?, feature_available_at?, raw_units?, transform_hash, values_hash | 당시 가용한 입력 |
| `predictions` | prediction_id, observation_uid, model_hash, research_score, probability?, decision_available_at, reasons | 불변 예측 기록 |
| `inspection_results` | inspection_id, product/shot key, numeric_label, semantic_label?, status, confirmed_at?, revision | 예측과 분리된 결과 |
| `queue_events` | item_id, ready_at, station_id, scheduled_at, started_at, completed_at, rule_source | 현장 데이터 확보 후 |
| `incidents` | incident_id, scope, event_type, severity, opened_at, owner, status | 점검 업무 묶음 |
| `actions` | incident_id, sop_id, sop_version, approved_by, action_type, performed_at, evidence | 조치 이력 |
| `validation_runs` | split_hash, data_hash, metric_protocol_version, scope, metrics_path, status | 평가 재현 |
| `deployment_approvals` | model_hash, policy_hash, contract_hash, scope, approved_by, expires_at, revoked_at | 범위별 적용 승인 |
| `audit_events` | actor, action, before_hash, after_hash, timestamp, reason | 변경 이력 |

`?`는 실제 값이 없으면 null이라는 뜻이다. 현장 기능의 필수 필드가 null이면 기능을 차단한다. 시험편의상 채운 시간·키를 실제 레코드에 섞지 않는다.

### 6.3 샷과 제품의 관계

같은 샷에서 여러 캐비티 제품이 나올 수 있다는 해석은 현재 상충 라벨의 **가능한 설명**이지 확인된 사실이 아니다. [S1 §1]

키가 확보되면 관계를 확인하고 모델 목표를 구분한다.

- 제품 단위 목표: 특정 제품의 최종 품질. 캐비티/제품 정보가 필요한지 검증한다.
- 샷 단위 목표: 그 샷에서 하나라도 품질 이상이 있는지. 제품 단위와 다른 목적이며 별도 지표다.
- 실제 검사 단위가 샷/로트라면 대기열도 그 단위로 구성한다. 행 단위 연구를 제품 단위 운영 효과로 그대로 바꾸지 않는다.

상충 라벨은 원본대로 유지하고 가능한 원인 목록으로 보관한다. 제품 결과를 샷으로 집계하는 실험을 해도 기존 행 단위 평가를 대체하거나 지표를 직접 비교하지 않는다.

### 6.4 시점 계약과 누수 방지

현장 기능에서 사용하는 각 특징은 `available_at <= prediction_cutoff_at`을 만족해야 한다. `event_time`만 빠르고 시스템 도착이 늦었던 데이터는 당시 예측에 사용할 수 없다.

- 샷 종료 후 모델: `shot_ended_at <= prediction_cutoff_at`이며 당시 필요한 요약값이 모두 도착해야 한다.
- 최종검사 결과, 이후 재작업, 최종 처분, 검사 소요시간의 확정값은 예측 입력이 아니다.
- 과거 검사 결과로 만든 이동 불량률은 각 과거 결과의 `confirmed_at/available_at <= cutoff` 조건이 필요하다.
- 시간대와 원본 시간은 보존하고 시스템 비교 시간은 일관되게 관리한다. 원본 시각의 시간대를 추정해서 채우지 않는다.
- 지연 도착 데이터로 다시 추론하면 새로운 prediction_id를 발행한다. 최초 예측을 과거 시점의 더 좋은 예측으로 덮어쓰지 않는다.
- 미래 전방분할은 실제 샷·배치 경계와 시간 간격을 반영해 사전에 고정한다.

학습/검증을 먼저 분리하고 표준화·특징 선택을 학습 범위 안에서 적합하는 원칙은 공식 scikit-learn 누수 방지 지침과 일치한다. [W1] 다만 공급자가 이미 수행한 사전 정규화의 누수 여부는 Pipeline을 추가하는 것만으로 해결되지 않는다. [S5 P0-B]

### 6.5 수신 오류 정책

현재 CLI의 엄격한 실패 동작은 보존한다. 필수열 누락·자료형/유한값 오류·해시 불일치가 있으면 성공한 추론 파일을 생성하지 않는다. 신규 서비스는 명시적 오류와 원본 격리 기록을 남긴다.

운영 연동에서는 AI 분석 실패와 현장 검사 유지가 동시에 성립해야 한다. 즉 AI 서비스가 죽어도 기존 검사 시스템의 원래 대기열을 삭제하거나 막지 않는다. 불완전한 AI 결과를 정상 결과로 응답하지 않는다. 재수신은 멱등 키로 중복 처리를 막고, 실패한 데이터의 라벨을 정상으로 채우지 않는다.

## 7. 안전한 정책 엔진과 검사 대기열

### 7.1 모드 정의

| 모드 | 목적 | 실제 검사 변경 |
|---|---|---|
| `RESEARCH_ONLY` | 기존 CSV/개발 산출물의 분석·비교 | 없음. 현재 기본값 |
| `SHADOW` | 실제 데이터를 읽되 추천은 독립 기록하여 검증 | 없음. 데이터 시점/단위 계약 필요 |
| `ADVISORY_APPROVED` | 범위별 검증과 현장 승인 후 참고 추천 | 승인된 범위의 사람 확인형 업무만 |
| `FALLBACK` | 오류·OOD·미검증·승인 만료·철회 | 기존 검사 유지 |

여기서 SHADOW 전환은 품질 예측 신뢰성 승인을 뜻하지 않는다. 측정 가능한 현장 입력을 수집·관찰하는 단계다. `ADVISORY_APPROVED`에서도 자동 설비제어·검사 생략·자동 정상 판정은 제공하지 않는다.

### 7.2 현장 참고 추천을 허용할 조건

다음이 모두 만족돼야 한다. 하나라도 미확인·실패하면 권한이 더 낮은 경로로 복귀한다.

1. 해당 파일/운영 원천의 라벨 방향·평가단위·스키마·변환기 계약이 확인됨.
2. 입력의 실제 가용 시점이 예측 cutoff 이전임이 확인됨.
3. 해당 설비 및 승인한 제품/레시피/조건 범위의 미사용 기간 검증이 승인 기준을 통과함.
4. 개별 입력이 유효하고 OOD·수집 지연·모델 장애가 없음.
5. 모델·정책·계약 버전에 연결된 현장 승인이 유효함.
6. 검사 자원·필수 규칙·대기 상한 등 운영 계약이 존재함.

전체 AP가 통과했다는 이유로 RG3를 포함시키지 않는다. 한 설비만 승인되는 부분 적용을 허용하며, 승인되지 않은 설비의 기존 검사 서비스 수준은 유지한다. 승인 범위는 해당 모델/정책/특징·전처리 버전에 귀속한다.

### 7.3 기본 결정 예시 — 설계 의사코드

```text
모든 차단 사유를 먼저 모은다.
입력 실패이면: 명시적 처리 오류 + 현장 기존 검사 불변.
RG3 등 미검증 설비이면: usual_inspection_unvalidated_machine.
OOD이면: usual_inspection_ood.
라벨 미확정이면: usual_inspection_label_unconfirmed.
그 외 계약/시점/승인/상태 문제이면: 사유별 기존 검사 유지.
운영 모드가 RESEARCH_ONLY/SHADOW이면: 실제 추천·대기열 변경 없음.
모든 조건과 범위별 승인이 충족되면: 사람 확인형 추천 생성.
어떤 경로에서도 검사 생략·자동 제어는 생성하지 않는다.
```

레거시 `action`의 우선 사유 순서는 기존 출력과의 호환을 검증하여 유지한다. 추가 사유는 `fallback_reasons[]`에 모두 보관한다. 예를 들어 RG3+OOD+라벨 미확정은 한 action만으로 나머지 제약을 숨기지 않는다. 상태코드의 이름보다 ‘권한 상승 금지’가 핵심이다.

### 7.4 정적 Top-K와 실제 운영 큐를 구별

기존 Top-K는 유한 평가 데이터 집합을 점수로 정렬한 지표다. 이를 ‘매 순간 대기열 10%를 자동 검사’로 그대로 이식하지 않는다. 실시간 큐에서 아직 도착하지 않은 제품을 후보에 포함하면 미래 정보 사용이다.

새 평가규약 제안은 다음과 같다. **기존 비교 결과는 기존 규약 그대로 보존한다.**

- 연구용 Top-q: `K = ceil(q * N)`로 명시하고 N=0이면 K=0. 같은 평가 범위의 모든 후보에 동일하게 적용한다.
- 동점: 결과 라벨과 무관한 안정적 해시 기반 순서, 고정 seed를 사용한다. 원본 행 ID 순서가 품질/시간과 연관될 수 있으므로 동점 민감도를 별도 보고한다.
- 전체 Top-K, 설비별 Top-K, fold×설비별 Top-K를 서로 다른 지표명으로 저장한다.
- 동점 규약이 기존 코드와 다르면 protocol_version을 바꾸고 신·구 수치를 병기한다. 새 정의로 과거 성능을 소급 수정하지 않는다.
- 같은 점수 척도가 보장되지 않는 설비별 점수를 직접 합쳐 전체 순위를 만들지 않는다.

### 7.5 운영 큐 정책 제안

우선순위는 단일 가중치 합보다 **제약 우선의 계층형 정책**으로 구현한다.

```text
현재 도착했고 검사가 가능한 대상만 생성
  → 승인된 필수·긴급 규칙을 우선 적용
  → 검사 자원 자격과 기존 서비스 배분을 보존
  → 대기 상한에 가까운 항목을 기존 규칙대로 보호
  → 승인된 설비·조건의 선택 가능 집합 안에서만 AI 순위 참고
  → 나머지는 현행 순서 유지, 동점은 기존 규칙/FIFO
```

새 승인 범위에서도 사람 승인 없이 기존 검사 시스템에 큐 변경을 쓰지 않는다. `operational_priority=null`인 항목은 자동으로 최하위가 되는 것이 아니라 **기존 정책 경로**로 간다. 최대 대기 상한과 설비별 자원 배분은 현장 계약에 따라 설정하며 임의 숫자를 기본 운영값으로 넣지 않는다.

### 7.6 알림 정책

알림은 모든 HIGH 행마다 발송하지 않는다. 동일 설비·문제유형·확인된 샷/로트 범위로 사건을 묶고, 확인 상태·재알림 조건·해제 조건을 둔다. 쿨다운이나 최대 알림량은 현장 검증 전 ‘미설정’으로 두며 미설정 상태에서는 실제 푸시를 켜지 않는다. 긴급 현장 알람은 AI 알림 제한 때문에 지연시키지 않는다.

## 8. AI 개발·고도화 규약

### 8.1 목적 함수를 업무와 맞춘다

기존 연구의 후보 선정 기준은 **개발 OOF AP**였다. 이를 유지하는 비교 트랙과, 새로 사전 정의한 **검사 역량 제한 회수율** 중심의 정책 연구 트랙을 분리한다. XGBoost shallow의 전체 상위10% 회수율 0.4545가 로지스틱 0.2727보다 높았다는 기록은 추가 가설의 근거이지만 AP·설비별 손실을 무시한 채 즉시 교체하는 근거는 아니다. [S4 표]

현장 큐를 위한 새 목적은 실제 검사 역량·제약과 연결해야 하며, 평가 결과를 본 뒤 유리한 지표로 바꾸지 않는다.

### 8.2 당장 할 네 가지 소규모 실험

| ID | 가설 | 제한된 비교 | 채택 판단 |
|---|---|---|---|
| H1 | class weighting이 점수 과신에 영향을 준다 | 동일 로지스틱 무가중/균형가중, 사전 고정한 소수 정규화 후보 | AP·설비별 회수율·확률손실 동시 평가 |
| H2 | 설비별 관계 차이가 누락돼 있다 | 통합 모델, 사전 지정 설비×특징 상호작용, 기존 설비별 모델 | RG3 변화와 CN7 손실, 계수 안정성 |
| H3 | 동일값 그룹 크기가 학습 비중을 왜곡한다 | 원래 행 가중치 vs 그룹 총가중치 동일화 | 행 단위 평가와 상충 라벨을 그대로 유지 |
| H4 | 일부 특징 의존이 불안정하다 | 학습 내부에서 정한 제한된 변수 묶음 제거 | fold별 중요도/계수, 일반화 손실 |

H3의 그룹 균등 학습은 예를 들어 각 행 기본 가중치를 `1 / group_size`로 줄 수 있지만 class weight와 결합 여부를 실험 계획에 명시한다. 평가 데이터의 행 수·정답을 바꾸지 않는다.

범위: 각 실험의 후보 목록, 선정 지표, 계산 예산을 시작 전 config로 기록한다. S5의 가설을 확장한 것이며 후보 수를 무제한 늘리지 않는다. XGBoost/LightGBM/CatBoost는 이미 비교한 대조군이다. 원시 시계열 없이 대형 시계열 모델·Transformer로 해결된다고 가정하지 않는다. [S5 P1-B]

### 8.3 평가 단위와 분할

- 기존 5-fold 그룹 분할은 비교 기준으로 보존한다. 예전 split manifest가 없으면 ‘같은 분할’이라고 단정하지 않는다.
- 새 후보의 파라미터·특징·보정·임계값·앙상블 가중치 선택은 외부 검증 fold를 보지 않는 내부 그룹 분할에서 한다.
- 개발 데이터는 이미 연구에 반복 사용됐으므로 중첩 검증을 추가해도 새 독립 시험셋이 아니다.
- 새 기간 확보 시 과거 학습 → 선택/보정 → 미래 평가를 사전에 고정하고, 실제 샷/배치/제품 중복을 차단한다.
- 시간분할에서 양성이 부족하면 기간을 사후에 유리하게 바꾸지 않는다. 평가 불가/불확실로 보고하고 추가 기간을 확보한다.
- 기존 480행 홀드아웃은 성능 튜닝·채택 결정을 위한 미사용 최종 평가로 재사용하지 않는다.

근거: S1 §2, S2, S5 P1-A·P2. 전처리·특징 선택의 학습 범위 제한은 W1 참고.

### 8.4 필수 평가표

| 묶음 | 지표/정보 | 주의 |
|---|---|---|
| 순위 | AP, 양성률, Top10%/20% 회수 수/전체 양성, Precision@K | AP를 일반 정확도로 부르지 않음 |
| 비교 | 기준선 대비 차이, 동일 단위 paired bootstrap 구간 | 고정 OOF에 조건부인 구간 |
| 설비/조건 | CN7/RG3 및 사전 지정 실패조건별 같은 지표 | 전체 평균으로 실패 숨기지 않음 |
| 표본 | 행·그룹·양성 수, fold별 수치, 사용/누락/보류 수 | 양성 0은 안전 증거가 아님 |
| 오류 | TP/FP/FN/TN와 임계값 출처, 오경보율·미탐률 | Top-K 밖과 임계값 FN은 다른 정의 |
| 확률 | Brier, Log loss, 신뢰도 구간표·구간별 표본 수 | 원점수/보정값/발생률 상수 구분 |
| 적용 | AI 허용 범위 비율, OOD·fallback 비율, 전체 정책 성과 | 허용 영역만 보고 전체 성과처럼 표현 금지 |

AP는 average precision 정의로 기록한다. 임의 사다리꼴 PR-AUC와 이름을 섞지 않는다. AP가 유병률보다 높다는 비교는 평가 집단의 숫자 양성률을 함께 보여주고, 다른 설비·기간 간 배율만으로 우열을 확정하지 않는다.

희소 양성의 bootstrap은 양성이 없는 재표집 처리, 유효 반복 수를 기록한다. 이미 읽은 개발 성능의 신뢰구간을 미래 현장 보증으로 표시하지 않는다. 고정 fold에서 seed만 바꾼 SD=0은 데이터 불확실성의 부재가 아니다. [S4, S5]

### 8.5 실패조건을 서비스 정책으로 연결하는 방법

먼저 RG3, OOD, 상충 라벨 그룹, 학습 내부에서 고정한 공정값 구간을 분석한다. 임계값 기반 오류와 큐 기반 회수 실패를 다른 표로 둔다. 조건별 양성이 적으면 그 사실을 먼저 표시한다.

새로 발견한 유리한 구간은 `exploratory`로 기록하고 독립 기간에서 검증하기 전 승인 범위로 자동 추가하지 않는다. 과거 검사 결과를 알아야 정의되는 ‘상충 라벨’ 같은 조건은 **사후 진단용**이고 온라인 승인 조건으로 그대로 쓰지 않는다.

원인 후보는 데이터 연결 문제, 관측되지 않은 공정 조건, 분포 차이, 희소 표본, 모델 표현력 중 어디에 증거가 있는지 구분한다. 센서명과 오류가 연관됐다고 물리 원인으로 확정하지 않는다.

### 8.6 확률·순위·변화감지를 분리

- `ranking_score`: 같은 모델·정책의 상대 순위에 쓰는 점수.
- `defect_probability`: 라벨 의미와 확률 검증이 해당 범위에서 승인된 경우에만 표시.
- `distribution_warning`: 학습 데이터와의 차이. 불량 판정이 아니다.
- `process_change_signal`: 실제 시간·단위·공정조건별 기준선에서 계산하는 변화 신호. 현재는 확장 대상.

보정은 순위 성능과 다른 목적이다. 공식 문서도 Brier/Log loss가 보정뿐 아니라 구분 능력·불확실성을 함께 반영한다고 설명한다. [W2] 기존 보정모델은 `deployment_approved=False`였으므로 자동 채택하지 않는다. [S3 §4–5]

### 8.7 비라벨 71,180행을 쓰는 범위

가능: 스키마·범위·분포 진단, 추론 파이프라인 부하 측정, 추가 라벨 확인 후보 선정, 연구용 순위 생성.

불가: 실제 불량률·재현율 계산, OOD를 정답으로 간주, 모든 행을 정상 라벨로 학습, 근거 없는 pseudo-label로 현장 성능 입증, 임의 시간 부여 후 조기경보 평가.

원본의 파일별 정규화 범위가 미확인이라 분포 차이는 물리적 공정 변화와 전처리 차이가 섞였을 가능성이 있다. 현재 OOD 38.43%를 ‘공장 불량 위험 38.43%’로 표현하지 않는다. [S1 §1·3]

### 8.8 후속 공정 중 모델

[조건부 확장] 원시 시계열을 확보하면 예측 cutoff를 ‘특정 단계 완료’처럼 먼저 정의하고, cutoff까지의 신호에서만 기울기·변동·면적·부분 최대값 등을 만든다. 현재 샷의 나중에 확정되는 전체 요약과 검사 라벨은 제외한다.

부분 시계열 특징+단순 모델을 먼저 비교하고, 충분한 독립 샷·불량 사례가 있으면 시계열 모델을 추가한다. 평가에는 최종 품질 구분뿐 아니라 **예측이 사용 가능해진 시점부터 유효한 대응 가능 시점까지의 시간**과 알림 부담을 포함한다. 모델 연산이 빠르다는 사실만으로 공정 중 개입할 시간이 있다고 주장하지 않는다.

## 9. 구현 아키텍처 및 API 제안

### 9.1 기존 저장소를 확장한다

[신규 제안] 새 프로젝트를 통째로 만드는 대신 기존 CLI와 모델을 중심으로 **단일 애플리케이션 + 얇은 웹 화면 + 실험 명령 분리** 구조를 먼저 만든다. 초기 범위에 별도 마이크로서비스, 메시지 브로커, GPU 서버, LLM 챗봇을 필수로 넣지 않는다.

기존 저장소에 웹 기술이 있으면 재사용한다. 없으면 제안 기본안은 Python API/서버 렌더링 화면과 로컬 SQLite다. FastAPI+Jinja 같은 조합은 선택지이며 현재 설치·동작을 확인한 기술 스택이 아니다. 다중 사용자 현장 단계에서는 인증·권한·중앙 DB·백업을 별도 검증한다. 모델 환경의 기존 lockfile을 이유 없이 업그레이드하지 않는다.

### 9.2 제안 디렉터리 — 기존 이름 충돌 시 조정

```text
moldguard.py                         # 기존 기준선 CLI 보존
calibration_diagnostics.py           # 기존 연구 경로 보존·인자 확장
task01_compare.py                  # 실제 파일명/위치는 저장소에서 확인

  adapters/legacy.py                # 기존 추론/산출물 어댑터
  policy.py                         # 승인·OOD·오류·모드별 fallback
  queue_policy.py                   # 현행 규칙 보존·참고 순위
  incidents.py                      # 사건·승인 SOP·조치 이력
  evaluation.py                     # 평가 규약·실패조건 조회
  registry.py                       # 모델/정책/계약 버전·승인
  repository.py                     # 저장소 접근·멱등·감사 로그
  api.py                            # 내부 API
  templates/                        # 얇은 화면 또는 기존 UI 재사용

  experiment_v2.json                # 실험 전 후보/지표/분할 고정

scripts/
  generate_split.py                # 제안: 학습 없는 분할 생성
```

### 9.3 외부 쓰기 범위를 제한한 API 계약

| 제안 API | 용도 | 실패/권한 조건 |
|---|---|---|
| `GET /api/v1/readiness` | 계약·모델·모드 준비 상태 | 미확정 상태를 사실대로 반환 |
| `POST /api/v1/research/score` | 레거시 데이터 연구 추론 작업 | 계약 버전·입력 해시·스키마 검사. 운영 추천 없음 |
| `GET /api/v1/research/rankings` | 기존 점수/순위/OOD 조회 | `research_only=true` 고정 |
| `POST /api/v1/operational/observations` | 현장 계약에 맞는 관측 수신 | 시점·키·변환기 미확정이면 거절 |
| `GET /api/v1/queue/recommendations` | 승인 범위의 참고 큐 | 미승인 항목은 기존 정책 경로 명시 |
| `GET /api/v1/failures/slices` | 평가 범위별 실패조건 | protocol/run/version·표본 수 필수 |
| `POST /api/v1/incidents` | 점검 요청 생성 | 품질 경보/데이터 경고/템플릿을 구분 |
| `PATCH /api/v1/incidents/{id}` | 상태·조치 기록 | 역할 검사·상태 전이·사유 기록 |
| `POST /api/v1/inspection-results` | 결과/정정 이벤트 수신 | 승인된 원천·키 검증. 추론 입력과 분리 |
| `GET /api/v1/validation/runs/{id}` | 검증·재현 결과 조회 | 연구/미사용 기간/재생/현장 평가 구분 |
| `POST /api/v1/approvals` | 범위별 참고 적용 승인 | 권한·근거·모든 게이트·만료 조건 필요 |
| `POST /api/v1/approvals/{id}/revoke` | 즉시 승인 철회 | 철회 후 신규 결정은 fallback |

모든 경로는 신규 설계이며 아직 실행 가능한 엔드포인트가 아니다.

`label_confirmed`, `machine_validated`, `deployment_approved`를 추론 요청자가 임의 전달한 값으로 신뢰하지 않는다. 서버가 버전별 계약·검증·승인 레지스트리에서 읽는다. UI에서 숨긴 버튼만으로 권한을 제어하지 않는다. 실제 설비 쓰기 API와 검사 생략 API는 만들지 않는다.

### 9.5 기술적 품질 요구

- **읽기 우선 통합:** 초기에는 기존 검사/설비 시스템에 쓰기 권한이 없는 방식으로 연결한다.
- **원자성:** 실패한 작업은 성공 산출물로 남기지 않으며 완료된 run만 조회 기본값에 포함한다.
- **멱등성:** 동일 원천 이벤트 재전송이 검사 결과·사건·예측을 의도 없이 중복 생성하지 않는다.
- **감사성:** 승인/철회·라벨 정정·SOP 변경은 전후 버전과 행위자를 남긴다.
- **복구:** 장애 후 모델·정책·입력 버전으로 당시 결정을 재생할 수 있어야 한다.
- **모델 파일 신뢰:** 임의 업로드된 직렬화 모델을 실행하지 않는다. 승인된 내부 아티팩트의 출처·해시를 확인한다.
- **성능 측정:** CPU 종류, 동시성, 배치 크기, p50/p95 지연, 실패율을 실제 실행으로 기록한다. 속도 목표값은 현장 필요와 기준 측정 뒤 합의한다.
- **데이터 보호:** 공정 원본·검사 결과를 기본적으로 외부 생성형 모델에 전송하지 않는다. 로그는 필요한 정보만 기록한다.

LLM 기능은 핵심 AI를 대체하지 않는다. 후속 선택 기능으로 넣더라도 승인된 SOP·검증 결과의 출처를 붙여 요약하는 범위로 제한하고, 근거 없는 원인·설정값·제어 명령을 생성하지 않는다.

### 10.1 지표별 근거 수준

| 지표 | 정의/분모 | 현재 가능 여부 | 필요한 추가 데이터 |
|---|---|---|---|
| AP·Top-K 회수율 | 지정 평가 집단/숫자 양성 기준 | 기존 개발 영역 연구 가능 | 실제 CSV·분할·예측 산출물 |
| 오류·fallback 비율 | 전체 관측 대비 각 오류·복귀 건수 | 연구 파이프라인에서 가능 | 입력 및 정책 결과 |
| 예측의 시간 여유 | 검사 확정 시각 − 결정이 사용 가능해진 시각 | 불가 | 변수 도착·예측·검사 확정 시각 |
| 불량 확인 지연 | 불량 제품 검사 확정 시각 − 검사 가능 시각 | 불가 | 실제 제품 키·ready/confirmed 시각 |
| 전체 검사 대기 | 검사 시작 시각 − 검사 가능 시각 | 불가 | 대기열·자원·검사 시각 |
| 확인 후 조치 지연 | 조치 수행 시각 − 사건 확인 시각 | 불가 | 실제 사건/조치 이력 |
| 반복불량 규모 | 사전 정의한 동일 조건·기간의 후속 불량/생산량 | 불가 | 생산수·샷/로트·확정 라벨·조치 시각 |
| 작업자 알림 부담 | 교대당 알림 수, 중복 비율, 처리 시간 | 현재 현장 수치 없음 | 교대·알림·확인 이벤트 |
| 작업환경 개선 | 탐색/기록 소요, 불필요 이동·재취급, 인지 부담 | 현재 현장 수치 없음 | 사전 정의한 관찰·사용성 평가 |
| 비용 효과 | 검증된 물량/시간 변화 × 실제 단가 − 추가비용 | 불가 | 인건비·폐기·재작업·운영비 실측 |

검사 가능 시각 대신 샷 종료 시각을 쓰고 싶다면 별도 지표명을 부여한다. 냉각·이송 등으로 검사 가능 시점이 다를 수 있으므로 혼용하지 않는다. 실제 현장에 그런 공정이 존재한다고 가정하지 않고 데이터 계약으로 확인한다.

### 10.2 오해를 막는 평가 원칙

**전량 검사를 유지하면 검사 횟수가 자동으로 줄어드는 것은 아니다.** 초기 목표는 같은 검사 역량 아래 의심 제품의 발견 지연을 줄이는 것이다. 작업자 업무도 알림·기록이 추가되면 오히려 늘 수 있으므로 알림 수, 처리시간, 중복 입력 부담을 함께 측정한다. 이는 제안 정책의 논리적 결과와 검증할 가설이지 이미 확인된 효과가 아니다.

불량 발견이 빨라져도 전체 대기시간이 증가하거나 특정 설비가 불이익을 받으면 채택을 보류한다. 최신 라벨 미도착 표본을 분모에서 임의 제거하여 성능을 낙관하지 않는다. 평가 종료 시 미완료 검사가 있으면 완료율·검열 상태를 보고한다.

재생 실험에서는 ‘정책 A에서 검사 완료가 정책 B보다 빠른가’를 비교할 수 있지만 생산 중단·조건 변경으로 미래 불량이 줄었을지는 별도 개입 효과다. 작업표준·제품군·설비·물량 변화 등 교란을 고려한 현장 비교가 필요하다. 안전한 기존 검사 아래 승인된 파일럿 범위를 설계한다.

### 10.3 채택 기준은 결과를 보기 전에 작성

다음은 승인 기준의 필드이며 숫자 목표의 달성을 약속하지 않는다.

- 데이터 게이트: 라벨·시점·단위·식별자·변환기 계약 전부 확인.
- 모델 게이트: 설비/승인 범위별 미사용 기간의 회수율·오경보·AP와 구간, 기준선 대비 허용 손실.
- 표본 게이트: 설비·조건별 필요한 양성 사례/평가 기간을 허용 불확실성에 맞춰 사전 합의.
- 정책 게이트: 필수검사 누락 0, 잘못된 자동 정상 판정 0, 비승인 제어 0, 대기 상한 위반 기준.
- 업무 게이트: 알림 부담·확인 시간·작업자 평가와 실제 개선.
- 복귀 게이트: 오류·OOD·만료·승인 철회 시 기존 검사 유지.

필수 숫자/범위가 미합의면 `acceptance_criteria`에 null로 남기고 현장 승인 불가로 처리한다. AP 0.5 또는 정확도 99%를 근거 없는 통과 목표로 넣지 않는다. 기준선 유지/현장 보류도 유효한 결론이다.

### 11.2 연구와 서비스 작업을 병행하는 순서

외부 데이터 회신을 기다리는 동안에도 재현 경로, 평가규약, 읽기 전용 화면, 정책 테스트, 빈 상태 처리, 사건 템플릿은 구현할 수 있다. 성능 미검증을 이유로 모든 개발을 중단하지 않되 미확정 항목을 임의로 채워 실제 운영 모드로 넘기지 않는다.

우선 첫 배치는 **P0 재현/계약 → 정책 엔진 → 연구 결과 조회**까지다. 두 번째 배치는 **실패조건 카드 → 사건 기록 → 제한된 모델 비교**다. 마지막으로 실제 데이터가 있을 때만 전방검증과 현장 큐를 연결한다.

### 11.3 기존 일정의 의미

S5에 기록된 **2026-10-03 재현 점검**은 새 환경 실행·분할 불변성·지표 재현·로그 완전성을 확인하는 목표다. **2026-10-06 내부 검토본**은 데이터 제약, AI 비교, 오류분석, 서비스 시연, 미해결 조건을 정리하는 목표다. 두 날짜 도달을 미래 성능·현장 승인 완료로 해석하지 않는다. 새 데이터가 없으면 P2/P3는 명시적으로 미검증 상태로 남긴다. [S5 §5]

## 12. 과제 제출 내용으로 연결하는 방법

S1이 정리한 15·40·15·10·10·10점 구성을 기준으로 서비스 관점을 연결한다. 이 배점은 첨부 보고서의 설명이며 이번 작업에서 공식 대회 양식을 다시 확인한 것은 아니다.

| 원문 평가 영역 | 제출에서 보여줄 것 | 서비스 증거 |
|---|---|---|
| 데이터 이해 15 | 라벨 불명확·상충 그룹·정규화·시점 문제 | 데이터 계약 센터, 데이터 요청 목록 |
| AI 개발/평가 40 | 기준선/강한 모델, 그룹 분할, 설비별 지표·불확실성 | 재현 실행·결과 비교·모델 선정 기록 |
| 영향요인/오류 15 | 어떤 조건에서 맞고 틀리는지, 해석 한계 | 실패조건 카드와 보류 사유 |
| 현장 활용 10 | 검사 전 의사결정, 표준 점검, 기존 검사 복귀 | 연구용 큐·사건 기록·승인 테스트 |
| 창의성 10 | 예측 후 확인/조치/검증의 연결, 실패 범위 명시 | 적용 제한·조치 추적의 일관성 |
| 코드/재현 10 | 새 환경 실행, 로그·해시, 검사 범위 공개 | CLI 인자·manifest·통합 테스트 |

서비스 UI가 모델 평가를 대신하지 않는다. 과제의 핵심 AI 평가와 실패조건 분석을 유지하고, 그 결과가 어떻게 업무 판단으로 이어지는지 시연한다.

발표 문구 제안:

> 기존 검사를 대체하는 자동 판정 모델이 아니라, 최종검사 전 먼저 확인할 대상을 선별하고 AI가 실패하는 조건을 함께 보여주는 작업자 지원 시스템을 제안한다. 현재 제공 데이터에서는 설비별 성능과 라벨·시점 제약을 공개하고 기존 검사를 유지한다. 이후 실제 샷·시간·검사·조치 데이터를 연결해 반복불량 대응과 생산성·작업환경 효과를 검증한다.

피해야 할 문구: ‘불량 예방률 90%’, ‘검사 인력 절반’, ‘모든 설비 정확도 99%’, ‘실시간 자동제어 완성’, ‘확률보정으로 RG3 문제 해결’, ‘OOD 38.43%가 불량 위험’.

## 13. 납품 및 완료 판정

### 13.1 내부 연구/서비스 개발 완료

재현 가능한 실행 경로, 데이터 계약 상태, 안전 정책, 읽기 전용 연구 화면, 실패조건 보고서, 사건 템플릿, 실행한 테스트·생략한 테스트·미해결 조건을 갖추었는지로 판단한다. 성능 수치는 실제 실행 산출물에서만 가져온다.

### 13.2 현장 참고 적용 완료

해당 설비·제품/레시피·데이터 원천의 계약, 새 기간 평가, 운영 제약, 작업자 확인 절차, 승인/철회·장애 복귀가 확인됐는지로 판단한다. 이 문서 작성 시점에는 **미완료**다.

### 13.3 실제 예방/생산성/작업환경 효과 검증 완료

검사 순위 변화뿐 아니라 조치 및 후속 생산·작업 기록으로 사전 정의한 효과를 검증했는지로 판단한다. 이 문서 작성 시점에는 **미검증**이다.
